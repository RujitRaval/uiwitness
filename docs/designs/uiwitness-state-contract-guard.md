## Vision

UIWitness should become the standard for UI product-state coverage. A repository records the states it promises, every pull request proves those states still exist and behave as expected, and every regression is locally reproducible without an account, hosted backend, required LLM, or automatic evidence upload.

### 10x Check

The next product is not a generic report comparator. It is a complete pull-request guardrail: a small reviewable state contract, deterministic comparison against fresh execution evidence, exact regression classification, a private offline comparison report, a first-class GitHub Action, and one-command local reproduction. Teams can adopt it even with known defects because exceptions are exact, owned, visible, and expiring. Later phases safely unlock authenticated applications and large sharded matrices without weakening deterministic behavior.

### Platonic Ideal

A developer opens a pull request. UIWitness runs the declared matrix and says either “all promised states survived” or names the exact route, state, viewport, theme, and contract rule that regressed. The failure includes a copyable local reproduction command. Unaccepted drift produces a compact candidate diff that becomes intentional only when explicitly accepted. Existing known failures cannot silently broaden or live forever. Authenticated runs reuse an ephemeral session without persisting secrets, and evidence is masked and retained according to explicit policy. Large suites shard deterministically, then fail closed if any shard is missing or inconsistent.

```text
CURRENT STATE                 THIS ROADMAP                     12-MONTH IDEAL
one-time evidence      ->     versioned state contracts  ->    product-state coverage standard
configured scans              PR guard + reproduction          trusted in every pull request
manual CI wiring              official GitHub Action           local-first ecosystem surface
public/per-cell auth          secure auth profiles              private-app coverage
```

## Accepted Scope

### Phase A — State contract foundation

- Add a small, versioned, human-reviewable contract format that records required matrix coordinates and their expected outcomes without storing screenshots or private evidence.
- Add a guard command that runs the existing configured matrix, compares the in-memory report returned by that same complete run with the contract, and returns stable machine and process outcomes for unchanged, regressed, unaccepted contract drift, invalid-contract, setup, and run-level states. Never fall back to a previous persisted report.
- Detect missing coordinates, unexpected matrix shrinkage, new failures, changed known failures, recovered failures, expired exceptions, and invalid or stale contract entries.
- Add an explicit accept workflow that updates only reviewed contract changes and produces a compact source-control diff. Never accept changes implicitly after a run.
- Extend selection to exact route, state, viewport, and theme coordinates and emit one copyable headed reproduction command for every regression.
- Add a separate schema-v1 contract-verdict sidecar and render it into the offline report without changing the existing schema-v1 execution report. Preserve the self-contained, no-network architecture and existing report readers.
- Include the minimum exact known-failure representation and expiry enforcement in Phase A so comparison semantics are internally complete; Phase C adds lifecycle tooling and richer governance surfaces.

### Phase B — Pull-request experience

- Publish a composite `action.yml` in this repository. Consumers pin the full release commit SHA (recommended) or an immutable full SemVer tag; mutable major tags are not published. The Action invokes the project-local `uiwitness` CLI and rejects version disagreement instead of reimplementing or silently downloading product logic.
- Produce a concise GitHub step summary and bounded annotations for exact regressions.
- Require only `contents: read`; add no write permission or implicit pull-request mutation. Keep evidence upload disabled by default. If enabled, warn that screenshots, URLs, and application data may be sensitive, default to one-day retention, and require an explicit retention value for anything longer.
- Cap annotations deterministically and put the complete result in the step summary. Point annotations at the matching committed contract entry when a reliable source range exists; otherwise use unlocated annotations rather than invented source positions.
- Preserve CLI parity so GitHub-specific integration never becomes the only supported workflow.

### Phase C — Known-failure governance

- Build lifecycle tooling and full reporting around the Phase A known-failure entry: exact contract identity, exact sorted failure-code set, owner, reason, creation date, and mandatory expiry.
- Fail when an exception expires, broadens, changes class, loses ownership, or masks a different coordinate.
- Surface recovered known failures as contract debt that must be explicitly removed rather than silently treating stale exceptions as healthy.
- Report active and expired exceptions in local output, offline HTML, machine JSON, and GitHub summaries.

### Phase D — Authentication and evidence privacy

- Add an explicit trusted-local authentication setup boundary that runs once per scan in a runner-owned setup context and seeds each fresh cell context from an in-memory Playwright storage state. Setup state must never touch disk, logs, errors, reports, or cleanup artifacts.
- Credentials originate only from user-controlled environment or secret-manager inputs and are consumed by trusted user-authored setup code. UIWitness neither solicits, stores, logs, nor uploads them.
- Permit storage state only for the configured application origin plus explicit additional origin allowlists; continue enforcing same-origin scan navigation.
- Add deterministic selector masking after readiness and before every screenshot attempt. Required masks fail closed when they match zero elements or violate declared cardinality.
- Add explicit `all`, `failures-only`, and `none` screenshot retention. Keep the existing schema-v1 report for `all`; introduce report schema v2 for policy-driven omission, with explicit omission reasons and tested v1 reading compatibility.
- Add evidence-manifest metadata describing retention, mask selectors by non-secret IDs, successful cardinalities, and capture policy without persisting masked content or secret values.
- Keep `.uiwitness/` ignored and private by default; keep all CI artifact upload explicit.
- Threat-model setup-code failures, expired sessions, redirects, multi-origin auth, missing masks, screenshot errors, and cleanup failures.

### Phase E — Deterministic scale

- Add stable one-based `--shard N/M` assignment derived from the first eight bytes of SHA-256 over the canonical coordinate key, interpreted as an unsigned big-endian integer modulo `M`.
- Write immutable partial bundles into distinct shard directories or CI artifacts; shards never contend for the current complete-report lock or publish into the final report tree.
- Add `uiwitness guard merge --input <bundle>...` to validate and merge partial reports without depending on completion order.
- Fail closed for missing, duplicated, mismatched-version, mismatched-contract, or overlapping shards.
- Evaluate the contract only after complete aggregation and preserve one deterministic final report.
- Support GitHub Action matrix orchestration without making GitHub a core-package dependency.

## Product Boundaries

- Remain local-first and deterministic.
- No hosted backend, account, cloud database, billing, required LLM, or telemetry.
- No pixel-diff baseline or hosted approval workflow; Playwright and dedicated visual-testing products already serve that category.
- No automatic hidden-state inference and no credential acquisition, management, or persistence; trusted user code remains outside that guarantee.
- No implicit contract updates, evidence uploads, exception renewal, or failure suppression.
- Public APIs remain small; browser-specific logic stays in the Playwright runner, contract logic stays browser-independent where possible, and GitHub integration remains an adapter over the CLI.

- Core validation, deterministic matrix expansion, stable coordinate and artifact identities, coverage math, schema-v1 report parsing, and stable error ownership.
- Isolated Playwright contexts, trusted scenario hooks, deterministic readiness, sanitized diagnostics, screenshots, assertions, resilient execution, and atomic private persistence.
- CLI configuration discovery, `init`, `check`, `scan`, `open`, route filtering, stable exit codes, and overwrite-safe promotion.
- A kinetic self-contained offline report with filters, deep links, keyboard behavior, and no network dependency.
- Documented GitHub Actions integration, protected release workflows, package-consumer gates, and exact public registry verification.

## Normative Implementation Contract

### Contract location, schema, and identity

The guard workspace root is the canonical real path of the CLI working directory; unlike ordinary `scan`, `guard` does not search parents. Its config, contract, scenarios, candidates, and explicit machine-output paths must resolve beneath that root through non-symlink regular-file/directory boundaries. This makes the portability and write boundary enforceable. The default committed source of truth is `<workspace>/uiwitness.contract.json`; `--contract <path>` may select another contained regular file. Contract files never contain screenshots, URLs with credentials, cookies, headers, storage state, console text, or failure messages.

```json
{
  "schemaVersion": 1,
  "configDigest": "sha256:4ad1...",
  "coordinates": [
    {
      "id": "home/public/desktop/light",
      "routeId": "home",
      "routePath": "/",
      "stateId": "public",
      "scenarioSource": "./scenarios/public.mjs",
      "viewportId": "desktop",
      "viewport": { "width": 1440, "height": 900 },
      "theme": "light",
      "configFingerprint": "sha256:ac72...",
      "expected": { "status": "passed" }
    },
    {
      "id": "settings/billing/mobile/dark",
      "routeId": "settings",
      "routePath": "/settings",
      "stateId": "billing",
      "scenarioSource": "./scenarios/billing.mjs",
      "viewportId": "mobile",
      "viewport": { "width": 390, "height": 844 },
      "theme": "dark",
      "configFingerprint": "sha256:731e...",
      "expected": {
        "status": "failed",
        "failureCodes": ["ASSERTION_FAILED"],
        "exception": {
          "owner": "checkout-team",
          "reason": "UIW-1842 tracks the billing-state repair",
          "createdOn": "2026-09-02",
          "expiresOn": "2026-09-16"
        }
      }
    }
  ]
}
```

- Each component ID already obeys the existing lowercase-kebab identifier rule, so the canonical coordinate ID is the literal `routeId/stateId/viewportId/theme` join. The ID must equal its four fields and be unique.
- The committed contract is pretty-printed with two spaces and one final LF for reviewability, but digests never hash presentation bytes. Parsed values must satisfy I-JSON and are canonicalized with RFC 8785 JCS: recursive UTF-16 code-unit property ordering, ECMAScript primitive serialization, preserved string data without Unicode normalization, UTF-8 output, and no insignificant whitespace. Domain arrays are sorted before JCS: coordinates by their four-field ID tuple and unique failure codes lexicographically by their ASCII enum values. A strict syntax-tree parse rejects comments, trailing commas, duplicate keys, lone surrogates, non-finite numbers, and negative zero before object conversion. SHA-256 over JCS bytes produces the digest.
- `routePath` in the contract and fingerprint uses the existing sanitized representation: WHATWG-normalized pathname plus query keys in original order with every value replaced by `[REDACTED]`; userinfo and fragments are absent. Raw query values never enter contract, verdict, candidate, or digest input, so value-only changes do not cause drift and must be represented by scenario state instead. This deliberately avoids even a one-way raw-value hash and its dictionary-attack risk.
- `configFingerprint` v1 is SHA-256 over this exhaustive ordered field set and no implicit fields: `routeId`; sanitized `routePath`; `stateId`; scenario source as a `./`-prefixed POSIX path relative to the workspace root after realpath containment validation; `viewportId`; integer `width`; integer `height`; `theme`; and the three effective `failOn` booleans (`consoleError`, `failedRequest`, `pageError`) after applying documented defaults. `baseURL`, hooks' source bytes, raw query values, credentials, environment values, CLI-only readiness timing, output paths, durations, and evidence bytes are excluded. Any future semantic config field requires a new fingerprint version and migration; “other runner behavior” is never inferred.
- `configDigest` is SHA-256 over the ordered set of coordinate IDs and their configuration fingerprints. A schema migration is an explicit parser/writer addition; v1 is never rewritten silently. Readers reject unknown schema versions with a stable validation finding.
- A passed expectation has no exception. A failed expectation requires an exact failure-code set plus non-empty owner and reason, ISO calendar dates, and an expiry later than creation. Failure messages remain diagnostic and are never contractual.

### Comparison truth table and precedence

The guard emits every applicable coordinate finding, then chooses one overall verdict by precedence. It does not infer whether drift was intentional.

| Contract | Current config | Fresh execution | Finding |
|---|---|---|---|
| malformed, duplicate, unknown version | any | none | `invalid-contract` |
| entry absent | coordinate present | complete | `unaccepted-addition` |
| entry present | coordinate absent | none | `missing-coordinate` / matrix shrinkage |
| entry present | same ID, changed fingerprint | complete | `unaccepted-config-drift` |
| expects pass | present, same fingerprint | pass | `matched` |
| expects pass | present, same fingerprint | one or more failures | `regression` with exact sorted actual codes |
| expects exact failure set, exception active | present, same fingerprint | same exact set | `matched-known-failure` |
| expects exact failure set, exception active | present, same fingerprint | different set | `changed-known-failure` |
| expects exact failure set, exception active | present, same fingerprint | pass | `recovered-known-failure` |
| expects failure, exception expired | present | any result | `expired-exception` plus the observed outcome |
| any valid entry | present | cell not executed because run was incomplete | `run-error`; no comparison or proposal |

Overall precedence is: invalid contract/config/setup, including malformed exception structure (`error`) → incomplete run (`error`) → unaccepted coordinate/config drift (`failed`) → expired exception (`failed`) → regression or changed known failure (`failed`) → recovered known failure (`failed`) → all entries matched (`passed`). Structurally valid but expired exceptions are contract failures; structurally malformed exceptions are invalid contracts. The sidecar retains lower-precedence findings so one failure never hides another. Contract acceptance converts reviewed drift into a new contract; fresh execution alone is always “unaccepted drift.”

An exception remains active through `23:59:59.999 UTC` on `expiresOn` and is expired starting `00:00:00.000 UTC` the following day. `expiresOn` may be at most 30 UTC calendar days after `createdOn`. Renewal is a newly generated and explicitly accepted exception change with a current reason; dates never extend automatically. The comparison receives an injectable UTC clock, stores `evaluatedOn` as `YYYY-MM-DD`, and uses that same date across all shards in a run set.

### Commands, outputs, and exit codes

```text
uiwitness guard [--config <path>] [--contract <path>] [--json <path>]
uiwitness contract init [--config <path>] [--contract <path>]
uiwitness contract inspect --candidate <path> --change <id>
uiwitness contract annotate --candidate <path> --change <id> --owner <text> --reason <text> --created-on <date> --expires-on <date>
uiwitness contract accept --candidate <path> --change <id>...
uiwitness scan --coordinate <route/state/viewport/theme> [--config <path>] [--headed]
uiwitness guard shard-plan --shards <M> --out <path> [--environment-id <id>] [--ttl <duration>]
uiwitness guard --shard <N/M> --shard-plan <path>
uiwitness guard merge --input <shard-bundle>... [--contract <path>]
```

- `guard` prevalidates configuration and contract before launching a browser. After successful setup it always performs a complete unfiltered fresh run in normal mode and compares only its returned in-memory report. `--json` selects a contained path that must not exist; it rejects symlink ancestors/targets and has no overwrite flag in v1.
- One extended final-publication transaction owns a generation's screenshots, execution report, contract verdict, immutable proposal, metadata overlay, evidence manifest, explicit `--json` copy, and HTML. Under the existing single lock it stages every file in a unique contained directory, validates cross-file digests and candidate acceptability, fsyncs, swaps the report/evidence generation with rollback bookkeeping, and makes HTML/stable pointers visible last. Any failure rolls the entire generation back. A proposal is acceptable only when its `sourceGenerationDigest` resolves to the committed generation marker; no orphan verdict or candidate can survive a failed publish.
- `--coordinate` is one atomic four-part selector. It must resolve to exactly one configured cell; it is for reproduction and cannot create or accept a whole-suite contract. Reproduction scans propagate only a non-default `--config`; guard/inspect/annotate/accept remediation propagates the relevant non-default `--config` and/or `--contract`.
- Exit `0` means the contract matched, including active exact known failures. Exit `1` means a complete run produced contract failures or unaccepted drift. Exit `2` means invalid inputs, setup failure, incomplete execution, unsafe write refusal, or internal error. This preserves the existing `0/1/2` public convention; detailed stable findings live in machine JSON.
- Browser-independent contract parsing, canonicalization, comparison, and verdict types are public only from `uiwitness-core`. The CLI orchestration surface remains process-based; the Playwright runner gains only typed complete-run and exact-coordinate inputs.

Minimal machine verdict:

```json
{
  "schemaVersion": 1,
  "verdict": "failed",
  "complete": true,
  "contractDigest": "sha256:...",
  "configDigest": "sha256:...",
  "runDigest": "sha256:...",
  "findings": [
    {
      "id": "home/public/desktop/light",
      "kind": "regression",
      "expected": { "status": "passed" },
      "actual": { "status": "failed", "failureCodes": ["CONSOLE_ERROR"] },
      "reproduce": "uiwitness scan --coordinate home/public/desktop/light --headed",
      "remediate": "uiwitness contract inspect --candidate .uiwitness/contract-candidates/sha256-....proposal.json --change regression:home/public/desktop/light"
    }
  ]
}
```

`runDigest` hashes a canonical semantic projection of the fresh report: coordinate identity, paths and scenario sources in normalized workspace-relative form, viewport, status, sorted failure codes, sanitized diagnostics, coverage, and logical evidence IDs. It excludes `generatedAt`, measured durations, host-specific base URLs and absolute paths, screenshot bytes, file mtimes, and shard run nonce. Contract, verdict, immutable proposal, metadata overlay, shard manifest, and normalized-report JSON all use the same canonical key/string/number rules. Findings sort by coordinate ID, then the explicit comparison-precedence order; duplicate coordinate/kind pairs are invalid. Proposal changes use the same order. Byte determinism means identical logical input, including `evaluatedOn`, yields identical bytes; full HTML and screenshots require semantic, not byte, equivalence.

Each finding supplies commands according to kind: executable `regression`, `changed-known-failure`, and `recovered-known-failure` findings get exact-coordinate headed `reproduce` plus proposal-specific `remediate`; structural `unaccepted-addition`, `missing-coordinate`, `unaccepted-config-drift`, and `expired-exception` findings omit `reproduce` and get `contract inspect` plus the precise rerun, annotation, or acceptance instruction. Commands always shell-escape paths and IDs.

### Safe initialization and acceptance

- `contract init` performs a complete fresh run. An all-pass result may create a new contract using the existing exclusive-file publication model: after full canonical bytes are buffered, open the final target with `wx`, write, fsync, and close. It never renames over a possibly created target. A reader that observes the writer's lock treats the file as in-progress and retries; without the lock, invalid/truncated bytes are a stable invalid-contract error. If any coordinate fails, initialization publishes only a proposal and empty metadata overlay as part of the complete generation transaction.
- The immutable proposal is canonical and content-addressed as `<sha256>.proposal.json`; its filename must match its recomputed bytes. It records `sourceGenerationDigest`, source contract digest (or `absent`), current expanded-config digest, run digest, tool/schema versions, completeness, and individually stable changes. A change ID is `<operation>:<coordinateId>`, where operation is exactly `add`, `remove`, `config`, `expectation`, or `exception`; at most one operation of each kind may exist per coordinate and collisions are invalid. Each change stores canonical `before` and `after` objects derived only from the source contract, current config, and fresh-run semantic projection.
- Users never edit the proposal. `contract annotate` writes a separately canonical `<proposal-sha>.metadata.json` overlay using the same safe contained publication rules. Its map is keyed by exact change ID and may contain only owner, reason, creation date, and expiry; the command validates each field and replaces metadata for only that named change. Distinct calls attach distinct metadata to multiple changes without changing the proposal hash.
- At acceptance, UIWitness recomputes every selected operation's `before` and `after` from the committed source generation, source contract, current config, and fresh-run projection; it rejects any proposal-field difference, unknown overlay key, digest/filename mismatch, incomplete or partial run, expired proposed exception, unknown change, current contract/config drift, unsafe target, or concurrent writer. It then merges only allowed overlay metadata, takes the exclusive lock, revalidates immediately before commit, writes a same-directory temporary regular file, fsyncs, and atomically renames. Creating the initial contract uses no-clobber semantics.
- A proposal is single-use. Acceptance applies only the selected changes, records unselected IDs as discarded, consumes its proposal and overlay, and requires a new complete `guard` run to reconsider anything else. This prevents a partial update from leaving a residual proposal bound to a stale source digest. It never renews an exception implicitly and never derives intent from a passing or failing run.

### GitHub Action delivery contract

- The repository root owns `action.yml`, its composite scripts, tests, changelog entry, and release tag. A release SHA identifies both Action adapter and package release. The Action checks that the project-local `uiwitness --version` equals the Action release version; mismatch is a setup error with an exact install command.
- Repository rules must prohibit update and deletion of release tags, and release CI verifies that the tag, GitHub Release target, package version, and recorded Action SHA are identical before publication. Documentation states that only a full commit SHA is cryptographically stable; a full SemVer tag is a human-readable convenience protected by repository policy, not an equivalent trust primitive.
- Inputs are limited to config path, contract path, artifact upload toggle, retention days, and annotation cap. The default annotation cap is 10 and the hard cap is 50. Totals and a deterministic bounded prefix remain in the step summary; the complete local sidecar is uploaded only through explicit artifact opt-in.
- Default permissions are `contents: read`. Fork pull requests receive no additional secrets or writes. Evidence upload uses the repository's pinned immutable artifact Action revision only after explicit opt-in.
- GitHub step-summary output is deterministically capped by UTF-8 byte length and finding count. It includes totals by finding kind, the first findings in canonical order, an explicit omitted count, and the local `.uiwitness/contract-verdict.json` path. The complete sidecar is uploaded only when artifact upload is explicitly enabled.
- Release verification adds a temporary consumer repository fixture that pins the Action SHA, installs the four packed packages from tarballs, runs a passing guard and a seeded regression, and proves CLI/Action verdict parity before the Action tag is published.

### Authentication, masking, and retention protocol

Phase D adds these browser-neutral fields to `UIWitnessConfig` in `uiwitness-core`; Playwright runtime hook types remain owned by `uiwitness-runner-playwright`:

```ts
interface AuthenticationConfig {
  setup: string;
  mode?: "shared-readonly"; // only supported v1 mode and default
  additionalOrigins?: readonly string[];
  cookieScopes?: readonly {
    domain: string;
    pathPrefix: string;
    secure: "required" | "permitted";
    partitionKeys?: readonly string[];
  }[];
}

interface EvidenceMaskConfig {
  id: string;
  selector: string;
  routeIds?: readonly string[];
  stateIds?: readonly string[];
  required?: boolean; // default true
  count?: number; // exact positive integer cardinality
}

interface EvidenceConfig {
  retention?: "all" | "failures-only" | "none"; // default all
  masks?: readonly EvidenceMaskConfig[];
}

interface UIWitnessConfig {
  // existing fields...
  authentication?: AuthenticationConfig;
  evidence?: EvidenceConfig;
}
```

```ts
export default defineConfig({
  baseURL: "https://app.example.com",
  failOn: { consoleError: true, failedRequest: true, pageError: true },
  routes: [
    {
      id: "settings",
      path: "/settings",
      states: [{ id: "billing", setup: "./uiwitness/states/billing.mjs" }]
    }
  ],
  themes: ["light", "dark"],
  viewports: { desktop: { width: 1440, height: 900 } },
  authentication: {
    setup: "./uiwitness/auth.mjs",
    mode: "shared-readonly",
    additionalOrigins: ["https://id.example.com"],
    cookieScopes: [
      {
        domain: ".example.com",
        pathPrefix: "/",
        secure: "required",
        partitionKeys: ["https://app.example.com"]
      }
    ]
  },
  evidence: {
    retention: "failures-only",
    masks: [
      {
        id: "account-email",
        selector: "[data-private='account-email']",
        routeIds: ["settings"],
        required: true,
        count: 1
      }
    ]
  }
});
```

- All config objects remain strict. IDs use the existing identifier grammar; module paths use workspace-contained real files; origin strings must normalize to an exact `scheme://punycoded-host:effective-port` with no credentials, path, query, or fragment; cookie domains are lowercase ASCII exact domains with an optional leading dot and no wildcard; path prefixes start with `/`; partition keys are normalized exact origins. Duplicate/unknown/empty values produce existing structured config issues at exact paths. Public-suffix rejection uses one mature, narrowly scoped Public Suffix List implementation and is the security justification for that dependency.
- `uiwitness-runner-playwright` exports `AuthSetup = (context: { context: BrowserContext; page: Page }) => Promise<void>`. A setup module default-exports that hook. It reads user-controlled secrets itself (for example from `process.env`), performs login, and returns no data; the runner calls `context.storageState()` without a path after success. Loader/shape/setup failures use `AUTH_SETUP_INVALID` or `AUTH_SETUP_FAILED`; output exposes only the stable code and non-secret module path.
- Phase D introduces coordinate fingerprint version 2. It includes every v1 field plus authentication mode, normalized setup path, additional origins, cookie scopes, evidence retention, and canonically ordered mask definitions/scopes. It never includes environment values or storage state. A v1 contract is still readable but requires an explicit generated v1→v2 contract migration before guarded Phase D behavior can pass.
- The evidence manifest is `.uiwitness/report/evidence-manifest.json`, schema version 1, and joins the single generation transaction. It records report/verdict/generation digests, retention, attempted/captured/omitted counts, and mask IDs with successful cardinalities only. Validation and runtime codes are stable: `AUTH_ORIGIN_NOT_ALLOWED`, `AUTH_COOKIE_NOT_ALLOWED`, `MASK_SELECTOR_INVALID`, `MASK_REQUIRED_MISSING`, `MASK_CARDINALITY_MISMATCH`, `MASK_APPLY_FAILED`, and `EVIDENCE_POLICY_INVALID`.

- A user-authored setup module receives the runner-owned page/context and reads user-controlled environment inputs directly. After the hook returns `void`, UIWitness captures Playwright `storageState` in memory once, validates it, injects a deep copy into each otherwise-fresh cell context, and drops all UIWitness-owned references after cleanup; it does not claim secure JavaScript-heap erasure.
- Local-storage records must match the base origin or an exact `additionalOrigins` entry. Cookies whose domain is the exact application host without a leading dot receive the implicit application scope; a leading-dot, parent, sibling, or additional domain requires an exact `cookieScopes` entry. Cookie domain matching follows RFC suffix semantics, path must begin with the configured prefix, `secure: "required"` rejects non-secure cookies, and a present partition key must exactly match an allowed normalized origin in that scope. Cookie ports do not exist and therefore cannot be allowlisted; origin records retain scheme and effective port. Public-suffix, malformed, unmatched, or unexpectedly partitioned cookies fail the run before cell contexts are created.
- UIWitness-owned serializers, loggers, errors, reports, verdicts, debug output, and temporary files never include cookies, local storage, auth headers, environment values, or setup return values. Auth setup failures cross the product boundary only as opaque stable codes plus non-secret module/location context.
- Setup modules are fully trusted arbitrary local JavaScript and can read, print, transmit, or throw secrets themselves. UIWitness cannot prevent that exfiltration; documentation and the threat model state this explicitly. The enforceable product promise is no credential acquisition, management, or persistence by UIWitness—not “no credential handling.”
- `shared-readonly` asserts that all cells may safely reuse one account without mutating shared server-side state. UIWitness cannot enforce behavior inside trusted hooks. Phase E rejects authenticated shard plans in v1; multiple roles, per-worker accounts, and authenticated sharding require a separately reviewed credential-provisioning protocol.
- For `all` and `failures-only`, every cell resolves applicable masks after readiness and attempts a masked screenshot before post-capture assertions, matching the current lifecycle. Required zero matches, invalid selectors, cardinality mismatches, or apply failures fail the cell and never fall back to unmasked capture. `SCREENSHOT_FAILED` remains possible. After final status is known, `all` retains all successful bytes; `failures-only` retains bytes only for failed cells and discards passing bytes before staging. Any additional failure-path attempt repeats mask resolution first.
- For `none`, the runner performs no screenshot or mask-resolution attempt, emits neither screenshot nor mask failure codes, and persists no image bytes. This behavioral difference is why retention participates in fingerprint v2. Masks are validated structurally at config load but DOM cardinality is not evaluated when capture is disabled.
- Schema v2 represents `screenshot: { status: "captured" | "omitted-by-policy" | "capture-failed", path? }`; the report reader accepts v1 and v2, while old v1 readers are documented as incompatible with privacy-mode output. The evidence manifest records policy and successful mask IDs/cardinalities, never selectors' matched text or DOM content.

### Shard wire protocol

- CLI indexing is one-based: shard `N/M` owns a coordinate when `uint64be(SHA256(UTF8(canonicalCoordinateId))[0..8]) mod M == N - 1`. Changing `M` intentionally redistributes coordinates; the algorithm and hash version are stored in every manifest.
- `guard shard-plan` first expands the complete current configuration inventory—not the contract inventory—and writes one coordinator plan containing a cryptographically random 128-bit run nonce, `createdAt`, `expiresAt`, `evaluatedOn`, shard count, complete ordered coordinate IDs, current config digest, contract digest, tool/report versions, and `targetDigest = SHA256(normalized baseURL origin + non-secret environment ID)`. `--environment-id` uses the existing lowercase-kebab identifier grammar and defaults to `default`. `--ttl` accepts whole-minute `5m` through `1440m`, defaults to `60m`, and is evaluated in UTC at shard start and merge; expired plans fail closed. Every shard receives the exact same plan. The nonce and timestamps separate fresh invocations and are excluded only from normalized semantic-equivalence comparisons.
- Each immutable shard bundle lives at `.uiwitness/shards/<run-set-id>/<n>-of-<m>/` locally or as the identical directory tree inside a CI artifact. `run-set-id` hashes the coordinator plan including nonce. It contains `manifest.json`, a validated partial report, its evidence subtree, and checksums. It never updates the final report pointer, and an existing bundle path is a hard error.
- The manifest includes schema/tool/report versions, `N`, `M`, algorithm version, ordered assigned IDs from the complete current config inventory, executed IDs, contract digest, config digest, target digest, nonce-bound run-set ID, creation/expiry/evaluation dates, report digest, and file checksums.
- `guard merge` sorts inputs by shard number, rejects missing numbers, duplicate manifests, overlaps, unassigned/missing executions, checksum failures, expiry, target/digest/version disagreement, and evidence path collisions, then compares the complete in-memory aggregate. Only the aggregator takes the extended final-publication lock and atomically publishes the complete generation: report, evidence, verdict, proposal/overlay, manifest, explicit JSON copy, and HTML. No proposal can be accepted from an unmerged partial.

## Success Measures

- A new repository can establish its first reviewed contract in under ten minutes.
- A pull request with no contract regression passes without human intervention.
- Every contract regression names one exact coordinate and provides a working local reproduction command.
- Unaccepted drift produces a small candidate diff, and only explicitly selected change IDs mutate the contract.
- Teams with known defects can adopt the guard without losing visibility or creating permanent exceptions.
- Authenticated runs persist no session secrets, and masking tests prove protected pixels never enter saved evidence.
- Sharded and unsharded runs produce byte-equivalent normalized semantic projections and contract verdicts; full reports and evidence are semantically equivalent.
- Product success is measured by repeat guarded runs per repository, 30-day repository retention, regressions fixed before merge, and contract expansion over time—not raw screenshot volume. Because UIWitness has no telemetry, these measures come only from opt-in user research, public-repository observation, or analytics owned and disclosed by the adopting repository; UIWitness itself collects none.

## Research Basis — 2026-09-02

- [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785.html) defines I-JSON-compatible canonical serialization, ECMAScript primitive rules, UTF-16 property sorting, UTF-8 output, and explicitly does **not** normalize Unicode strings. Its verified errata add negative-zero rejection. This supersedes the plan's initial custom canonicalization proposal.
- The RFC lists the JavaScript [`canonicalize`](https://www.npmjs.com/package/canonicalize) implementation; npm currently reports version 4.0.0, TypeScript declarations, zero dependencies, and 529 dependents. Microsoft's [`jsonc-parser`](https://www.npmjs.com/package/jsonc-parser) currently reports stable 3.3.1 and exposes a syntax tree/visitor suitable for rejecting duplicate keys before ordinary object conversion. Both remain subject to exact Node 22/24, license, integrity, provenance, and packed-consumer verification before acceptance.
- GitHub states that full commit-SHA pinning is the only immutable Action reference, recommends minimum explicit permissions, and warns that tags can move: [security hardening](https://docs.github.com/en/code-security/tutorials/secure-your-organization/protect-against-threats), [custom Action release management](https://docs.github.com/en/actions/how-tos/create-and-publish-actions/manage-custom-actions).
- GitHub documents that fork `pull_request` runs receive read-only tokens and no secrets, while checking out untrusted code under `pull_request_target` or `workflow_run` can expose the repository: [compromised runners](https://docs.github.com/en/actions/concepts/security/compromised-runners), [secure use](https://docs.github.com/en/actions/reference/security/secure-use). Environment approval delays secret access but does not make arbitrary checked-out code safe: [environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments).
- GitHub treats context strings such as branch names and pull-request text as untrusted injection sources and caps each step summary at 1 MiB: [script injection](https://docs.github.com/en/actions/concepts/security/script-injections), [workflow commands](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands). The plan uses argv-only inputs and a 512 KiB safety budget.
- Playwright recommends shared authentication only when tests can safely use the same account concurrently, warns that saved state can impersonate the user, and supports seeding isolated contexts from storage state: [authentication](https://playwright.dev/docs/auth). UIWitness therefore uses memory-only state, documents the shared-read-only limitation, and defers authenticated sharding.
- Playwright supports screenshot locator masks and notes they cover invisible matched elements: [screenshot API](https://playwright.dev/docs/next/api/class-page). UIWitness adds required-selector/cardinality validation because masking alone does not prove the intended private element was found.
- Playwright's sharding model uses one-based `N/M` shards and a separate merge job over per-shard reports: [sharding](https://playwright.dev/docs/next/test-sharding). UIWitness adds nonce, target, inventory, expiry, and checksum binding because contract acceptance requires stronger same-run completeness.
- Chromatic owns cloud baseline review and explicitly warns that dependency-based selective testing can miss changes and is unlocked only after successful CI history: [PR workflow](https://www.chromatic.com/docs/in-pull-request/), [TurboSnap setup](https://www.chromatic.com/docs/turbosnap/setup/). UIWitness therefore keeps full promised-state execution and does not enter pixel-baseline approval or automatic impact selection.
- Playwright already provides ARIA snapshot contracts and patch-based snapshot updates: [ARIA snapshots](https://playwright.dev/docs/aria-snapshots). UIWitness does not duplicate that surface in this roadmap; accessibility snapshots remain a future composable signal only after the state-contract guard proves adoption.

| Path | Nil/missing | Empty | Error | Happy path |
|---|---|---|---|---|

### Stateful objects

```text
GENERATION
prevalidated -> executing -> staged -> cross-validated -> committed
      |             |          |              |
      +-------------+----------+--------------+-> failed -> rollback/recovery
committed -> replaced-by-next-generation

PROPOSAL
derived -> committed-with-generation -> optionally annotated -> accepted -> consumed
   |                 |                         |             +-> selected changes only
   |                 +-> generation rollback -> invalid
   +-> partial/incomplete run -> forbidden
expired/stale/digest-mismatch -> rejected (never returns to reusable)

SHARD RUN SET
planned -> active -> bundles-complete -> validated -> aggregated -> published
   |         |              |              |
   +---------+--------------+--------------+-> expired/invalid -> terminal failure
```

Impossible transitions are prevented by schema validation, digest binding, one-way consumed markers, exclusive locks, no-clobber bundle paths, and the committed-generation marker. A failed or partial shard set cannot produce an acceptable proposal.

### Coupling, scale, failure, and rollback

- **Intentional coupling:** the runner's persistence input broadens from report/evidence to a core-defined generation bundle. It does not learn CLI parsing, GitHub behavior, or contract mutation logic.
- **10× scale:** sequential browser work and HTML/evidence size break first; Phase E shards execution while deterministic summary caps protect GitHub output.
- **100× scale:** local disk, aggregate memory, and browser startup dominate. The wire protocol permits streaming validation later, but distributed storage or hosted coordination remains explicitly outside this roadmap.
- **Single points of failure:** the contract file and final generation coordinator are authoritative by design. Source control restores contracts; the existing rollback generation and lock recovery restore evidence.
- **Security architecture:** all external strings cross strict core schemas; trusted JavaScript is explicit; browser secrets remain runner-memory state; output containment, symlink refusal, HTML escaping/CSP, and opt-in upload preserve the local boundary.
- **Representative integration failures:** Action/CLI mismatch fails before browser work; authentication failure yields an opaque setup code; a killed writer leaves a recoverable staged generation; a missing shard blocks publication; report rendering failure rolls back the whole generation.
- **Rollback:** each phase can revert its focused PR and prior release SHA. Contracts are versioned source files; Phase D can disable auth/privacy fields and use schema v1; Phase E can return to unsharded `guard`; Action consumers can pin the prior known-good SHA. No database or remote-state migration exists.
- **Platform quality:** canonical browser-independent contract/verdict/proposal/shard schemas are the reusable seam. A future runner or CI adapter consumes those schemas while the first implementation stays deliberately concrete.

| Filesystem escape | `..`, absolute paths, symlinks, hard links, output replacement | canonical workspace containment, real-directory boundaries, regular-file checks, `wx` create, same-directory staging, existing lock/recovery model | symlink/TOCTOU/permission/ENOSPC suite on supported OSes |
| Evidence leakage | route tokens, unmasked pixels, browser state, diagnostics, public artifacts | existing query-value redaction, required masks fail closed, no unmasked fallback, memory-only auth, local ignored storage, opt-in uploads with one-day default | secret canaries in URLs/DOM/storage/logs plus artifact inspection |
| HTML injection | config/diagnostic strings become active markup or script | reuse escaping and hash-based CSP; no untrusted inline event handlers; no network assets | hostile report fixture under CSP and no-script mode |
| Denial of service | huge contract, selector, message, or summary consumes memory/platform quota | bounded string lengths, coordinate counts, diagnostic sizes, 512 KiB hosted summary, canonical truncation with totals | boundary and one-over-limit tests |

Security-sensitive maximums are normative: 10,000 coordinates per unsharded/aggregate contract, 1,024 characters per owner/reason/path/selector field unless an existing stricter limit applies, 30 days per exception, 24 hours per shard-plan TTL, 512 KiB per Action step summary, and no implicit evidence upload. Larger local matrices require an explicit future limit review rather than unbounded parsing.

The protected authenticated workflow uses an environment with required reviewers and branch restrictions, but approval is an operational gate—not a sandbox. A maintainer must review the exact commit and promote it to a trusted branch before any user-authored module receives secrets. Self-hosted runners are not recommended for untrusted contributions.

## Review Section 4 — Data Model & User Experience

**Result:** six edge-case decisions resolved. The model has one source of truth, one complete fresh-run projection, one verdict, and one atomic generation; no shadow database or remote state exists.

### Core invariants and edge cases

| Input/state | Required behavior |
|---|---|
| Missing contract | `guard` exits `2` with `contract init`; only initialization may proceed without it |
| Empty contract/config/matrix | invalid before browser launch; never treated as all-pass |
| Duplicate JSON keys or coordinate/change IDs | invalid at syntax/domain validation; never last-write-wins |
| New configured coordinate | execute it because inventory comes from config, then emit `unaccepted-addition` |
| Contract-only coordinate | emit `missing-coordinate`; exact scan is impossible, so show inspect/remediation only |
| Same coordinate, changed runtime inputs | `unaccepted-config-drift`; no execution outcome can silently accept it |
| Multiple actual failure codes | unique exact sorted set; messages remain diagnostic |
| Known failure recovers | guard fails as contract debt until explicit removal |
| Exception reaches expiry | active through the named UTC date; blocks starting next UTC day; maximum 30 days |
| Run ends mid-matrix | no comparison, no proposal, no new visible generation |
| Proposal partially accepted | selected changes commit; proposal is consumed; fresh complete run required for the rest |
| Evidence policy `none` | no screenshot or mask DOM work; report v2 explains policy omission |
| Very large finding set | complete local JSON/HTML; deterministic bounded terminal/GitHub prefix plus totals |
| Clock differs across shards | coordinator's `evaluatedOn` governs all shards and merge |
| Same config against another environment | target digest prevents cross-origin/environment merge |

### End-to-end user journeys

```text
FIRST CONTRACT
install -> configure -> contract init -> complete run
  all pass -> exclusive contract creation
  failures -> immutable proposal -> annotate exact exceptions -> accept named IDs

PULL REQUEST
guard -> fresh full matrix -> compare
  matched -> exit 0 + calm report
  regression/drift/recovery/expiry -> exit 1 + exact finding + remediation
  invalid/incomplete/unsafe -> exit 2 + previous generation retained

INTENTIONAL CHANGE
guard -> inspect proposal -> reproduce executable cells -> annotate if needed
      -> accept named IDs -> review compact JSON diff -> fresh guard proves match

AUTHENTICATED CONTRIBUTION
same-repo trusted branch -> protected environment approval -> memory-only setup -> guard
fork -> secret-free guard -> maintainer reviews exact commit -> trusted branch -> protected guard

SHARDED RUN
shard-plan -> parallel immutable bundles -> merge all -> one comparison -> one generation
```

The product vocabulary is fixed: **matched**, **regression**, **unaccepted drift**, **known failure**, **recovered known failure**, **expired exception**, **invalid setup**, and **incomplete run**. “Intentional” appears only after acceptance. Terminal, JSON, HTML, and GitHub use the same terms and counts.

No telemetry is added. Adoption and retention metrics may be learned only through opt-in interviews, public repository observation, or analytics explicitly owned by adopters.

## Review Section 5 — Code Quality & API Discipline

**Result:** the research corrected one material flaw: replace bespoke canonical JSON rules with RFC 8785 JCS. Two narrowly scoped runtime dependencies are recommended only after the normal package audit and Node 22/24 compatibility gate.

- `uiwitness-core` owns strict contract/verdict/proposal/overlay/manifest schemas, JCS adaptation, domain ordering, SHA-256 digests, comparison, finding precedence, and exported immutable types.
- Use exact reviewed pins of `canonicalize` 4.0.0 for RFC 8785 serialization and stable `jsonc-parser` 3.3.1 in strict JSON mode for syntax-tree offsets and duplicate-key detection, provided license, provenance, Node 22/24, ESM, size, and package-smoke checks pass. They have no product-network behavior. If either gate fails, stop and revisit; do not silently implement a partial standard.
- The persisted JSON remains human-readable. Digest functions operate on validated logical objects, not formatting bytes, and expose versioned algorithms such as `jcs-rfc8785+domain-v1`.
- `uiwitness-report` consumes only core schemas and renders pure HTML. It does not compare contracts or read the filesystem.
- `uiwitness-runner-playwright` owns browser/auth/mask/capture and the single generation transaction. It accepts a core-defined generation bundle but does not parse CLI flags or GitHub context.
- `uiwitness` CLI owns argument validation, orchestration, terminal rendering, and mutation commands. It never reimplements schema or comparison rules.
- Public APIs are additive and documented. Internal write/recovery primitives remain internal. Unknown schema/fingerprint/hash versions fail explicitly; no heuristic migration occurs.
- No catch-all silently converts programmer errors into product matches. Exhaustive discriminated unions and `never` checks cover every verdict, operation, state, and stable failure code.
- Comments explain invariants and threat boundaries, not line-by-line mechanics. New dependencies receive architecture justification and immutable lockfile integrity.

## Review Section 7 — Performance & Scale

**Result:** three scaling risks mapped and bounded. The plan optimizes only after complete coverage is guaranteed.

- **Execution dominates:** browser navigation and capture are orders of magnitude larger than contract comparison. Phase A stays sequential to preserve current behavior; Phase E adds cross-machine sharding, never hidden in-process concurrency.
- **Authentication:** one setup per scan removes repeated login cost. Because Playwright recommends shared auth only for non-mutating shared-account tests, authenticated sharding is rejected in v1 rather than racing one account across workers.
- **Comparison budget:** strict parse, canonicalization, and comparison must process 10,000 coordinates in under 1 second and under 256 MiB additional RSS on supported Node versions using a release-build benchmark fixture. Normal 100-cell contracts target under 100 ms excluding filesystem access.
- **Report budget:** transform and render 10,000 result rows without quadratic lookup or string concatenation. The HTML may be large but must remain bounded by the existing diagnostic caps; a benchmark records bytes, render time, and peak RSS.
- **Mask budget:** applicable selectors resolve once per screenshot attempt after readiness. No polling beyond existing readiness; exact cardinality counts operate on a locator snapshot at capture time.
- **Shard assignment:** stable hash assignment prioritizes minimal movement when coordinates are added. Fixed fixtures measure imbalance; warn when the largest shard exceeds 1.5× the mean, but do not reassign dynamically or use historical durations because that would break reproducibility.
- **Merge:** validate manifest headers and checksums before loading reports/evidence, reject oversized or duplicate inputs early, sort only bounded metadata, and preserve order-independent output. Streaming aggregation is deferred until the 10,000-coordinate benchmark demonstrates a real need.
- **Hosted output:** 512 KiB summary, 20 detailed findings, 10 default annotations, and 50 maximum prevent GitHub presentation from becoming the bottleneck. Full findings stay local.
- **No impact selection:** full promised-state execution remains the trust model. Chromatic's own caution around selective dependency analysis reinforces deferring changed-file selection until substantial successful-run evidence exists, and it remains outside this roadmap regardless.

Performance regressions are gated with repeatable local benchmarks recorded by Node version and platform. Wall-clock browser thresholds are broad enough to avoid CI noise; deterministic algorithmic and artifact-size assertions are exact.

## Review Section 10 — Trajectory, Reversibility, and Deferred Bets

**Result:** reversibility **5/5**. The roadmap creates stable local protocols without committing to a hosted control plane, proprietary baseline, or framework monopoly.

### Dream-state delta

| Milestone | What becomes true | Remaining gap to 12-month ideal |
|---|---|---|
| Phase A | repository has an enforceable, reviewable state promise and exact reproduction | CI adoption still requires manual workflow wiring |
| Phase B | one thin Action makes guard status native to pull requests | known-failure maintenance remains manual |
| Phase C | imperfect repositories can adopt without permanent silent quarantine | private apps still need secure setup |
| Phase D | authenticated product states gain memory-only sessions and evidence policy | one shared-read-only role; no auth sharding |
| Phase E | large public/read-only matrices shard and merge deterministically | no hosted collaboration, impact analysis, or multi-run analytics |

The end state is a credible product-state coverage standard, not a generalized testing platform. The contract/verdict protocol is reusable; Playwright remains the first runner; GitHub remains one adapter. Pixel baselines stay with Playwright/Chromatic, ARIA snapshots stay composable rather than duplicated, and Storybook remains a possible input adapter rather than the product center.

### Deferred candidates for `TODOS.md` after draft approval

1. **P2 — Multi-role and authenticated-shard credential provisioning**
   **What:** define user/admin role profiles and one externally supplied account per shard without UIWitness owning credentials.
   **Why:** unlock large protected-state suites and role-specific contracts without shared-account races.
   **Pros:** materially expands enterprise usefulness; resolves the explicit Phase D/E seam.
   **Cons:** high security and lifecycle complexity; secret-manager adapters risk platform coupling.
   **Context:** Playwright recommends distinct accounts when tests mutate server-side state; v1 intentionally supports one shared-read-only session and rejects authenticated sharding.
   **Effort:** Human L (~1–2 weeks) → Codex+gstack M (~1–2 days). **Depends on:** repeated Phase D adoption and a fresh security/engineering review.

2. **P3 — Optional ARIA snapshot signal adapter**
   **What:** let a coordinate reference user-authored Playwright ARIA snapshots as another eligible product assertion.
   **Why:** accessibility structure can complement screenshots and explicit assertions.
   **Pros:** richer state contracts using an existing Playwright standard.
   **Cons:** duplicates mature tooling if UIWitness owns snapshot generation or approval.
   **Context:** Playwright already provides YAML ARIA snapshots, partial matching, and patch updates; UIWitness should compose rather than reimplement.
   **Effort:** Human M (~3–5 days) → Codex+gstack S (~4–6 hours). **Depends on:** guard adoption and demand for cross-signal reporting.

3. **P3 — Storybook/MSW coordinate adapters**
   **What:** map existing stories or MSW scenarios into explicit UIWitness coordinates without automatic discovery.
   **Why:** reduce setup for teams already maintaining component states.
   **Pros:** lowers adoption friction and broadens framework reach.
   **Cons:** framework/version maintenance and overlap with Storybook's own test ecosystem.
   **Context:** Storybook already runs render and interaction tests; UIWitness's differentiated value would be unified state-contract governance, not another story runner.
   **Effort:** Human L (~1 week) → Codex+gstack M (~1 day). **Depends on:** stable contract import API and real adopter requests.

4. **P3 — Conservative impact selection**
   **What:** research a verifiable changed-file-to-coordinate selection mode with forced full-run checkpoints.
   **Why:** very large suites may eventually need less work per commit.
   **Pros:** lower CI time and cost at scale.
   **Cons:** a false negative silently skips a promised state—the worst possible guard failure.
   **Context:** Chromatic itself gates TurboSnap behind successful history and warns about missed changes; this roadmap always runs the full matrix.
   **Effort:** Human XL (~3–4 weeks) → Codex+gstack L (~3–5 days). **Depends on:** measured Phase E bottlenecks, safe full-run cadence, and a separate approved roadmap.

5. **P3 — Streaming aggregate/report rendering**
   **What:** stream validated shard records and incremental report sections instead of retaining a 10,000-coordinate aggregate in memory.
   **Why:** remove the next scale ceiling only if benchmarks show memory pressure.
   **Pros:** supports much larger local suites.
   **Cons:** complicates deterministic ordering, rollback, and renderer purity.
   **Context:** current target is bounded at 10,000 coordinates/256 MiB; no evidence yet justifies the complexity.
   **Effort:** Human L (~1 week) → Codex+gstack M (~1 day). **Depends on:** Phase E benchmark failure.

Recommended disposition: record all five as evidence-gated follow-ups, build none in this roadmap. Interactive acceptance UI, SaaS review, telemetry, pixel diffing, automatic state discovery, and a plugin marketplace remain skipped rather than backlog commitments.

**Result:** UI scope is material. The proposed experience fits `DESIGN.md`; design readiness improves from **8/10 to 9.5/10** with the contract-first hierarchy below. A live `/design-review` remains mandatory after implementation.

### Report information architecture

```text
┌─────────────────────────────────────────────────────────────────────┐
│ UIWITNESS / CONTRACT VERDICT                            [run digest] │
│                                                                     │
│ PROMISE KEPT  or  CONTRACT BROKEN                                  │

└─────────────────────────────────────────────────────────────────────┘
```

- **Hierarchy:** contract verdict and counts lead; actionable findings come next; the existing evidence matrix and inspector remain intact below. Do not convert the report into a generic dashboard or floating metric cards.
- **Status language:** `PROMISE KEPT` uses restrained signal green; regressions and invalid evidence use the existing vermilion signal fracture; active known failures and approaching expiry use warning amber; neutral selected forensic focus uses blue. Color is never the only cue.
- **Evidence privacy:** masked regions use opaque report-void `#0b0c0a`, not failure red or Playwright's default magenta, so privacy treatment does not imply regression. The report names mask IDs/counts outside the image without exposing matched content.
- **Commands:** every executable finding has a copy control plus selectable plain text. Structural findings show inspect/remediation instead of fake reproduction. Copy feedback lasts 120 ms, is announced through a polite live region, and has a no-script text fallback.
- **Layout:** full-bleed ruled regions, bone/void evidence surfaces, IBM Plex/Georgia/system-monospace fallbacks, tabular counts, square structural edges, and one dominant evidence object follow the industrial-editorial system. At under 760 px, findings become one stream; at 320 px no horizontal page scroll is permitted.
- **Motion:** only 120 ms control and 220 ms state transitions connecting a matrix cell to evidence; fully disabled under reduced motion; no animated evidence, parallax, or autoplay.
- **Accessibility:** semantic headings/table/list structure, skip link, visible focus, keyboard filters and details, URL-restorable state, `aria-describedby` for expected/actual outcomes, live result count, non-color status labels, 44 px touch targets where practical, and WCAG AA contrast. No-script mode exposes all findings and details.
- **Large suites:** filters and counts stay operable with thousands of findings; the report never hides the existence of truncated terminal/GitHub entries. Deep links use stable coordinate/finding IDs.
- **Design verification:** render every verdict/finding/privacy state at desktop, 760 px, and 320 px; compare against `DESIGN.md`; run keyboard/screen-reader/no-script/reduced-motion checks; then execute `/design-review` on the generated report and fix all material drift before release.

## NOT in Scope

- **Pixel-diff baselines or screenshot approval:** Playwright and Chromatic already own this category; UIWitness contracts state coverage and expected outcomes.
- **Hosted review, accounts, billing, or cloud evidence:** conflicts with the local-first product and is not needed for PR enforcement.
- **Required LLM or AI-generated assertions:** weakens determinism and creates a network/model dependency.
- **Automatic state discovery or changed-file impact selection:** a false negative can silently skip a promised state; full matrices remain mandatory.
- **Saved authentication-state files:** contain impersonation-capable credentials; v1 auth remains memory-only.
- **Authenticated sharding or multiple roles:** requires externally provisioned per-shard accounts and a separate security design.
- **Performance/accessibility snapshot ownership:** dedicated tools already exist; future UIWitness adapters may compose their output after demand.
- **Plugin marketplace or fifth publication package:** no second runner/adapter has proven the abstraction or maintenance cost.
- **Interactive acceptance UI or bulk accept:** named single-use change IDs are the v1 safety surface.
- **Telemetry or remote operational dashboard:** success learning remains opt-in and external to the product.
